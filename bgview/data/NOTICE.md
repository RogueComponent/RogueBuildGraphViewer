# `schema-facts.json` — provenance

`schema-facts.json` is **bgview's own file**, not Epic Games'. It is a derived table of the
three facts bgview reads out of the BuildGraph schema:

| Fact | Consumed by |
|---|---|
| which element names exist | `known_element` → D14 (unknown element kind) |
| which attributes are typed `TagListType` / `TagType` (R2) | `is_tag_output` → the entire dataflow model |
| which attributes carry `use="required"` | `is_required` → D11 (required attribute resolves empty) |

Nothing else in the schema is read by any detector, so nothing else is carried. No types, no
documentation strings, no structure — 98 element names and their producing/required attribute
names, extracted mechanically.

## Why it is not Epic's `Schema.xsd`

Earlier versions of bgview vendored a copy of

```
Engine/Build/Graph/Schema.xsd      (UE 5.8)
```

That file is generated by Unreal Engine and owned by Epic Games, and it is distributed under the
Unreal Engine EULA rather than under bgview's licence. bgview is published openly — a public
repository and a public web app — so redistributing it was not bgview's to do. The derived table
replaces it: a description of the interface bgview targets, which is the same thing any compatible
tool has to know, in bgview's own format and under bgview's own licence.

**No Unreal Engine file is vendored in this repository.**

## Why the table exists at all

`bgview` derives its entire tag-polarity model from the schema — an attribute typed `TagListType`
produces tags, anything else containing a `#Name` consumes them. Without a schema there is no
analysis at all, so requiring one would break the "no UE install required" constraint for the most
common case: pointing the tool at a script someone emailed you.

That fallback tier is essential rather than convenient (R28/V29): `Schema.xsd` is **generated and
gitignored**, so it is frequently absent even from a real engine checkout.

## Version drift — read this

The schema is regenerated by the engine and changes as Epic adds or alters tasks. A derived table
can therefore disagree with the engine version that actually runs your script.

Resolution order is: `--schema` → walk-up discovery from the script path → this table. So whenever
the script lives inside a real UE tree, **that tree's schema wins** and this file is never read.
The CLI prints a note to stderr when it falls back, and the web app says so in its footer.

If you analyze scripts for a different engine version, pass `--schema` explicitly, or regenerate
the table (below) from that version's schema.

## Regenerating

Generate the schema from your own engine tree, then derive the table from it:

```
RunUAT.bat BuildGraph -Schema=<output path>
python tools/derive_schema.py <output path> --engine 5.8
```

That writes both copies — `bgview/data/` for the CLI and `webapp/data/` for the site, which has to
be a self-contained directory a static host can serve as-is.

`tests/test_schema.py::DerivedFactTableTests` asserts the table agrees with a real `Schema.xsd`
element for element and attribute for attribute, so a stale table fails the suite rather than
quietly changing what bgview reports.
